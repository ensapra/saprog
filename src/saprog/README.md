# Saprog joint snapshots

## Desktop home

The **9DoF IMU** tab is a Python ROS display backed by the independent **C++ `imu_node`** on Linux/WSL. ROS owns serial I/O, sample parsing, filtering, calibration and zero; the UI subscribes to topics and calls services. Closing the tab preserves the backend and its zero until Home closes. The backend detects the SparkFun device at 115200 baud, can attach an already-shared USB device to WSL, and sends one Space toggle if valid samples do not arrive. Magnetic heading is optional and off by default. See [How the IMU works](IMU.md) for the sensor explanation, fast-motion limitations, topics/services, units, launch commands and URDF mounting considerations.

Home opens with a live **Temperature Monitor** showing all servo temperatures on one graph. Toggle individual servos, or use **Select all** and **Deselect all**. Colored labels identify each trace and show its latest temperature in Celsius. The graph retains the last five minutes, including history for hidden servos, scales to the selected readings, and marks readings stale after 2.5 seconds without updates. Missing readings create gaps instead of implying continuous measurements. No plotting dependency is required.

Home starts the shared controller when it opens so the monitor receives readings immediately. The readback node publishes `sensor_msgs/msg/Temperature` messages on `/saprog/temperatures`, one per successful servo read, with the servo name in `header.frame_id` and temperature in Celsius. Monitoring does not issue movement or torque commands.

Use **Time window (seconds)** to select a preset (including 10 or 20 seconds), or type any duration from 1 to 300 seconds and press Enter or **Apply**. **Zoom in** halves the visible duration; **Zoom out** doubles it. The graph continues following live data and retains five minutes of history when zoomed in, so zooming back out restores the wider view immediately.

Home, Creator, and Player use a shared dark theme. Both snapshot windows have general **Movement speed** (1–1023) and **Torque strength** (0–1023) sliders. Their values apply to every joint in subsequent movement commands: Creator's Move and Load Snapshot, and Player playback. Sliders do not change an ongoing movement or already holding servos; Creator's Fix service continues to use controller defaults. Zero strength is rejected before movement. Speed starts at 1023; Creator strength starts at 1023, and Player retains its saved strength preference. The windows keep their own settings. Restart Home to rebuild the updated controller and windows together.

Position commands may include a velocity array in radians per second, using 0.111 rpm per AX speed unit. Every velocity must map to 1–1023 and all joints in a command must share the same speed; an omitted array uses the configured moving_speed. The existing effort array supplies raw torque limits. Snapshot files still contain positions only.

The desktop windows share consistent colors, typography, and spacing. Home retains launcher buttons between directory changes; Player checks file metadata during automatic refresh and only rebuilds its list when files change. Manual Refresh always reloads snapshot names, and playback always reads and validates the selected file again. Repeated telemetry and status values do not repaint unchanged controls, preserving status text selections while the message stays the same.

Home builds the complete workspace before opening its window; ROS, `colcon`, and `flock` must be installed. If the build fails, Home stops before launching stale installed applications.

Run `bash ./launch_home.sh` from the workspace to build all workspace packages once and open the home window. Selecting a window does not rebuild; it attaches USB if needed and starts the shared controller. The controller stops after the last window closes or when Home closes. You can also run `bash ./tabs/launch_snapshot_creator.sh` or `bash ./tabs/launch_snapshot_player.sh` directly; direct launchers do not rebuild and start/clean up their own controller. Re-run Home after source changes to rebuild the installed windows and backend.

On WSL, selecting a window from Home automatically attaches the configured USB serial adapter before starting ROS. The device must be shared with WSL in usbipd-win on Windows. If usbipd reports it is not shared, open an elevated Windows PowerShell and run `usbipd bind --busid 1-2` (use the adapter's current BUSID). The launcher does not detach it when the app closes. By default it selects the FTDI adapter `0403:6014`; use `SAPROG_USB_BUSID=1-2` to choose a specific device, or `SAPROG_USB_HARDWARE_ID=0403:6014` to override the hardware ID. The configured `device_name` path is checked and must appear as a character device before ROS starts.

To add a window, put a `*.sh` launcher in `tabs/`. It appears in the home window automatically. A launcher can use the shared `tabs/_launch_window.bash` helper to preserve workspace setup, controller readiness, and cleanup behavior; pass `window` and the name of its installed executable under `lib/saprog/`.

The **Snapshot Creator** window arranges leg controls in a robot-view grid: front left (31–33) and front right (11–13) above back left (41–43) and back right (21–23). It shows the latest telemetry and a writable target in radians for each joint. Enter a value and choose **Move** to send that joint target; the controller validates the position and enables torque while moving. Each joint has one toggle that reads **Fix** while released and **Release** while fixed. The bottom status message is selectable and can be copied with Ctrl+C. The **Snapshot Player** window has the same copyable status area.

The package installs a small Tk desktop window for naming, saving, and replaying robot poses. Start the ROS nodes with the same configuration file used by your setup:

```sh
ros2 run saprog saprog_nodes --ros-args --params-file /path/to/saprog.yaml
ros2 run saprog snapshot_window
```

When the ROS backend starts, it leaves servo torque unchanged and publishes the observed torque state alongside each joint reading. The window marks already torque-enabled joints as **Release** in green and released joints as **Fix** in red. You can fix or release any joint; **Fix** reads its current hardware position and enables torque holding there. A failed or unavailable hardware operation is reported in the window.

Set `status_return_level` in `config/saprog.yaml` to match the servos (1 or 2); the controller does not change this EEPROM setting. At level 1, unicast register writes use transmit-only packets followed by register readback instead of waiting for a write acknowledgement that the servo will not send. Multi-servo speed, torque-limit, and torque-enable settings are synchronized and verified, then cached so unchanged settings are not resent. Multi-servo position goals are synchronized; per-servo goal-register readback is disabled by default to keep updates fast. Set `verify_goal_registers: true` for commissioning or debugging; it adds one serial read per servo per synchronized command. Single-servo position requests are still verified. Goal-register readback confirms the target was accepted, not that the joint reached it; arrival still requires fresh position telemetry. Errors report failed writes/readbacks. Check power, cabling, servo ID/baud rate, Status Return Level, and competing serial-port users when communication fails.

Enter a name and choose **Save targets** to save the values displayed in the target fields for every joint. All targets must be finite numbers within the measured joint ranges. Snapshots save typed radian targets in schema version 1. Previously saved schema version 2 snapshots remain readable. Saving does not require torque to be enabled or fresh telemetry, and does not move the servos. Files are JSON in `snapshots/` at the project root; `--directory PATH` selects another folder. Saving over an existing filename asks before replacement.

Use **Browse** to choose any JSON snapshot, then **Load Snapshot** to validate it and start playback. The **Fixed** option is on by default and keeps torque holding the loaded targets. Turn it off to release torque only after every configured joint has reported a fresh target position within 0.03 rad for at least three samples spanning one second. Both modes send all joint targets together using a synchronized command. If target arrival telemetry is stale, incomplete, or times out after 30 seconds, the window reports incomplete movement and leaves torque enabled. Torque release happens asynchronously and is reported complete only after every servo acknowledges it. The window never claims a position was reached until telemetry confirms stable arrival. Invalid, incomplete, non-finite, mismatched, or out-of-range snapshots are rejected before any command is sent. Closing the window does not change motor torque.

## Timeline

Each transition has a **Duration** selector: **Until reached** (the default for new and existing timelines) or **X seconds**. Until reached advances on fresh telemetry confirming target arrival. X seconds sends the motion commands, then advances when the specified duration expires regardless of arrival or missing telemetry; decimal seconds and zero are accepted. This controls when the next step starts, not how quickly the servos travel. Speed sliders still determine movement speed, and a following command can replace an unfinished target. Duration settings are saved with each transition. Separate Wait rows remain available for pauses after a transition completes under its selected duration rule.

**Custom Control** uses the same robot-view grid as Snapshot Creator: front left (31–33) and front right (11–13) above back left (41–43) and back right (21–23). Each leg contains individual speed and torque sliders for its servos. The panel scrolls vertically when needed.

Timeline playback adds no default dwell between poses. Until reached requires fresh telemetry confirming arrival; controller polling and communication latency can affect when arrival is detected. X seconds instead uses the transition timer. Snapshot Player retains its separate stable-arrival behavior.

Enable **Loop timeline** to repeat the complete sequence until **Stop sequence** is pressed. Each pass includes all waits and leaves torque unchanged between passes; the after-timeline torque action is not run while looping. Any failure stops looping. **Test selected step** still runs once. The loop choice is saved with the timeline and defaults to off for new and older files.

The timeline-wide **After timeline** dropdown selects **Torque on** or **Torque off** for all servos when the complete, non-looping timeline finishes successfully. It defaults to on and is saved with the timeline. Playback waits for every torque service acknowledgement before reporting completion. Failure, timeout, Stop, close, and looping skip the after-timeline action. Commands already sent may still finish. **Test selected step** does not run this timeline-end action.

Playback leaves the current torque state unchanged when it starts and between transitions. If torque is off before playback, it is not enabled automatically. Select **Torque off** after the timeline to release all configured joints at successful completion. Torque-on actions use the controller's hold-current-position service and controller speed/strength defaults; transition sliders apply to the moves.

Use **Add wait** to insert a separate **Wait** row after the selected transition/snapshot pair or wait (or at the end when nothing is selected). Click the Wait row and enter its **Duration (seconds)**, including decimal values such as `2.5`. Durations must be finite and non-negative; zero skips the delay. **Up**, **Down**, **Duplicate**, and **Remove** also work with waits. Waits can appear between transition/snapshot pairs, at the beginning, or at the end.

A wait starts when the preceding transition finishes under its duration rule (target arrival or elapsed time). Playback shows the remaining time, sends no servo commands during the wait, and leaves torque unchanged. **Stop sequence** cancels the wait and prevents the next step from starting. **Test selected step** can test a wait on its own. Wait durations are included in saved timelines and restored on load.

Restart Home to install the new **Timeline** launcher, or run `bash ./tabs/launch_timeline.sh` after building. You can also run `ros2 run saprog snapshot_player --timeline`. Timeline uses the same controller configuration and hardware limits as Player.

Choose an available snapshot and **Add available snapshot**, or browse with **Add snapshot…**. The sequence always alternates **Transition → Snapshot → Transition → Snapshot**. A timeline stores each snapshot's file reference, not a copy of its pose; editing a snapshot therefore changes the pose used the next time the timeline is played. Click a transition to open its settings; snapshot rows show the destination. Use **Up**, **Down**, **Duplicate**, and **Remove** to arrange transition/snapshot pairs, including repeated poses. Settings follow their destination when reordered. The first transition starts at the robot's current pose.

Each transition has a dropdown with **Global Control**, **Leg Control**, and **Custom Control**. Global shows one speed slider and one torque-strength slider for all servos. Leg shows a pair for each leg: front left (31?33), front right (11?13), back left (41?43), and back right (21?23). Custom shows a pair for every servo. Sliders range from 1 to 1023; there is no torque on/off setting.

Switching from Global to Leg or Custom copies the current global values to every affected servo. Switching from Leg to Custom copies each leg's values to its three servos. When combining differing values into Leg or Global, the new sliders use their rounded arithmetic average. Edits and the selected control mode are saved with each transition. Older timelines with torque on can still load; legacy torque-off transitions are rejected rather than silently changed into powered movement.

**Play timeline** validates every pose against the connected robot, then submits the complete sequence to the ROS `/saprog/play_timeline` action. The ROS controller owns playback; the Tk window only submits the goal, displays feedback, and requests cancellation. Each transition applies per-joint speed and torque settings, then sends all joint targets in one synchronized position packet, even when individual speeds differ.

Timed transitions and waits use a monotonic ROS-side worker clock, not GUI callbacks. A timed transition's duration begins after its synchronized position command has been transmitted; the next step cannot start before that full interval has elapsed. **Until reached** advances on a fresh complete joint-state sample confirming arrival. Scheduled timeline commands take priority over new background bus reads, but a bus transaction already in progress can still delay a command. If the worker wakes more than 20 ms late, or the serial bus stays busy for 250 ms after the command becomes due, playback aborts. Once it acquires the bus, it completes speed/torque preparation and sends the position packet even if preparation itself takes longer; later steps remain serialized and timed from the actual packet transmission. This is deterministic scheduling with overrun detection, not a hard real-time guarantee: Linux scheduling, USB/serial latency, and servo mechanics can still introduce physical timing variation. The timeline reports failure and skips its end-torque action after an overrun or other failure.

**Test selected step** submits only the selected transition or wait and does not run the timeline-end torque action. **Stop sequence** requests ROS action cancellation; no later motion steps or end-torque action are started, though a command already being transmitted may finish. On successful full non-looping completion, the ROS action performs the configured after-timeline torque operation and reports success only after the hardware operation is acknowledged. Cancellation is rejected once that final operation has begun.

**Save timeline** writes a versioned JSON document containing snapshot file references and transition settings, without copying snapshot data. References are resolved in the configured snapshot directory; snapshots selected outside that directory retain their absolute file path. Keep referenced snapshots available when loading or playing a timeline. Older timelines that embedded poses are migrated on load when a matching snapshot file is present. Save timelines separately from the snapshot directory. Offline editing and save/load work without a controller; hardware playback requires one. The editor checks for unsaved changes before New, Load, or closing.

## Snapshot player controls

Run `ros2 run saprog snapshot_player` to open a separate window with one button for each JSON snapshot. It discovers additions and removals automatically and also has a **Refresh** button. Use **Browse** and **Load Snapshot** to load a file outside the snapshot directory. The player reads the same `snapshots/` at the project root directory as the snapshot window; pass `--directory PATH` to use another folder. Set **Torque strength** from 0 to 1023 before playback; this sets the AX torque limit for each commanded joint (1023 / 100% on first use; slider changes are saved automatically and restored on restart). Preferences are stored separately from snapshots in `~/.config/saprog/snapshot_player.json` (or `$XDG_CONFIG_HOME/saprog/snapshot_player.json`; on Windows, `%APPDATA%/saprog/snapshot_player.json`). **Disable torque on all joints** requests torque off for every configured servo and reports any failures.

The player waits for controller calibration and a subscriber on `/saprog/position_command` before enabling snapshot buttons. The **Fixed** option has the same behavior as the snapshot window: on keeps torque holding targets, while off waits for fresh stable arrival telemetry before requesting acknowledged release for every joint. Clicking a snapshot button or choosing **Load Snapshot** re-reads and validates the complete file, then sends all joint targets together in a DYNAMIXEL Sync Write packet so the servos start moving together. `target_tolerance` in `config/saprog.yaml` (default 0.05 rad) controls both allowed synchronized goal-register readback error and arrival tolerance; increase it to allow more joint-position variance. Restart the controller after changing it.


## Hardware limits and target units

Hardware limits are read from each servo's CW/CCW angle-limit registers at controller startup and again whenever Creator or Player opens. The window calls the controller's `/saprog/refresh_limits` service, sharing its serial connection. Limits are kept in memory only; they are not stored in the YAML configuration. Failed reads are reported and retried; position commands require a successful complete read.

To inspect the limits separately with the controller stopped, run `python3 scripts/read_servo_limits.py` after sourcing ROS. This utility prints the limits without changing configuration or servo settings.

Creator displays and accepts radians. Measured hardware limits are displayed to three decimal places; validation uses their full precision. Both Creator and Player validate snapshots against these limits.

ROS `/saprog/position_command`, telemetry, and target-arrival tolerances use radians.

Arrival checking in Creator and Player uses `target_tolerance` plus half an AX encoder tick for goal rounding. Fresh finite telemetry slightly outside a configured limit can still confirm arrival; command targets remain strictly limited. During playback the status shows the worst remaining joint errors or missing/stale telemetry. If fresh readings make no progress toward outstanding targets for eight seconds, playback reports incomplete movement without releasing torque. Zero torque strength is rejected before Player playback.
